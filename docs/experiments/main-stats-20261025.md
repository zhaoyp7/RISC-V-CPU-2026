# 当前main IPC统计（2026-10-25）

## 测量对象与验证

基于main 7c3b345，功能RTL同ba7ceb6 / main-freq-age-matrix-20261025。
配置W2/ROB16/PRF48/RS8/CDB2/LSQ16、LSU在途队列8项、双bank I$各1KB；latency=10，MAX_CYCLES=50,000,000。
普通版与LOCAL_STATS版独立构建，两版均通过官方make perf的六项答案检查，stdout、输入hash及周期逐项相同。
ROB提交计数逐项等于benchmark instructions，所有模块计数周期等于CPU2026 cycles。
W2 IPC geomean **0.522108164152558**，与现有主线记录一致。

只新增可选工具和独立input-only bind监视器，未修改功能RTL、官方filelist、Makefile或scripts。
当前24个综合输入hash仍与既有diagnose/opt报告一致；不新增综合或改变456.12 MHz / 19,808.712 µm²结果。

## 核心结论

1. **load等待暴露与ROB小窗口压力是当前最明显的现象。** qsort/rsort队首load未完成占51.12%/55.37%周期，
其中已发出请求等待返回占37.90%/48.56%，pending/query只占5.63%/1.93%。队首load在IQ等待源位为零。
这定位到访存返回延迟在提交窗口暴露，不能进一步推断“所有外存等待都可通过某项优化消除”。
2. **ROB双路预留有明显待验证机会。** 入口条件为count+W<=DEPTH；W2下count=15就停止接收，
不只是count=16。qsort/rsort仅剩1槽分别占21.36%/29.43%周期；真正满16项为21.46%/27.98%。
这些是容量状态占比，尚未测量这些周期是否恰有单条可接收，不能当作可回收IPC收益。
3. **旧的“未知store地址阻塞主导”结论已不适用于当前组合。** 活跃load执行级因消歧受阻仅0～1.24%周期，
其中qsort还存在partial，不能只统计unknown。现有架构已经把大量消歧阻塞与其他工作解耦。
4. **registered wake仍有优化机会，但不是已证明的单一根因。** 有本拍CDB唤醒可形成完整候选、而当前没有
issue offer的周期为1.35%～17.80%。要实际提前发射，还需要数据前递和资源准入；不能把这些周期直接折算为IPC增益。
lane1不支持当前所选指令占3.58%～20.73%，尚未证明同拍有其他可发ALU候选，属于候选方向而非确定收益。
5. **分支仍值得后续关注。** median/qsort/towers误预测率约17.9%/21.8%/34.5%。本次未测量每次误预测的
完整恢复代价，ROB recovery计数仅覆盖恢复门控周期，不能直接当作全部分支损失。

下一步建议先评估ROB仅剩1槽时的接收机会，并结合load关键依赖链与有效窗口利用率制定对照；
如评估扩大窗口，需要同时考虑PRF容量及面积成本。本轮只完成统计，不实施这些功能改动。

“pending但无有效R”包含查询流水填充、选择和重试，不等于全部都是无谓气泡。
有效请求等待ready几乎为0，反映当前并非主要卡在请求准入；这不等于内存访问没有返回延迟。
